1 Summary

The problem. When a fibre cut or a tower fault happens, SkyLink's network team knows within minutes and customer care does not. Agents run the same reboot script, and 30% of these calls end in an unnecessary technician visit costing $650 (brief, p.1). The architect's part is to link network events, which arrive as a stream, to customer contacts, which ask and wait, and to decide what rules, machine learning and a language model each do.

The architecture. Five programs from one container image share one PostgreSQL database. The API (front desk) returns a complaint reference after one database write. The orchestrator (coordinator) works each case with five specialist agents that can read SkyLink's systems and cannot change them. The feed consumer (the radio) applies the network's numbered events. The executor (the hands; the brief's Action agent) holds the only write key. Staff decide at the staff desk (the human gate). The MCP server lets other assistants ask, and never act.

The brief asks for an event-driven plus request-response architecture, hybrid with on-premises systems. Figure 1, on the next page, shows the system as built. Each kind of traffic has its own line.

The credit path, with the human gate above $500

Two examples, by the policy file. A plan of $999 a month, out for 5 hours: 999 × 5 × 1.0 ÷ 720 = $6.94, raised to the policy's minimum of $50.00 and paid without review. 6 Data and knowledge

Stores1 databasePostgreSQL 17, on Amazon RDS in the demonstration. 21 tables, and the workflow library's own.
Vectors1 tableguide_chunks, through pgvector: 96 guide sections (12 guides × 8), each as text and as 256 numbers.
Customer details in vectors0Only guide text is stored as vectors. A customer's message is hashed in memory for a search and not kept.

The one vector search, in full

  1. Filter by the customer's own router, as named on the service record, never by the customer.
  2. Filter by section. Four of a guide's eight sections are safe to follow alone: no internet, Wi-Fi, slow speed, power cycle.
  3. Rank by keyword rules for the kind of fault, matching words, and closeness of the vectors. At most four rows are left, so each is compared exactly.
  4. Quote, never rewrite, with guide, section and version.

What is kept where

  • In the database: cases and messages, the work queues, an audit log that can be added to and never changed, the network picture, reference identifiers, the guide index.
  • Not in the database: the CRM profile (name, mobile, email, consent) and Billing's credits, read when needed and not stored. Stored: the phone line a contact centre states, and the customer's own words.
  • In versioned files: the credit policy and the guides; the index is rebuilt from them.

7 Cloud: what runs where, the choice, the cost and the release

SkyLink's core systems stay on its premises, and the care platform runs in the cloud. Three programs may cross the boundary between them: the orchestrator to read, the feed consumer to listen, the executor to act. Figure 5 sets what runs today beside the design for a pilot.

AWS or Azure

The choice is AWS, in the Mumbai region (client decision D4 of the execution plan, 22 November 2026), for three reasons. The team had access to AWS, the action plan's reference target, so it was the shortest safe route to a running demonstration. Nothing in the design is tied to one cloud: the programs are containers and the data is PostgreSQL with pgvector, and both run the same way on Azure. And Mumbai keeps the demonstration close to the team and the audience, in an Indian region. We do not claim that AWS is cheaper or better in general. A real choice for SkyLink should compare its own skills, private connectivity to its data centres, access to language models and measured cost.

How a release is built, scanned, deployed and rolled back

  1. Verify. Code style and types, the test suite with its 80% coverage gate, the seven evaluations, a scan for leaked secrets.
  2. Build and scan. One container image, scanned by Trivy. A HIGH or CRITICAL weakness that has a fix fails the job.
  3. Publish. The image goes to ECR under its commit, a name that never moves, so a rollback gets what was tested.
  4. Deploy. One command on the server starts the release from a clean state and plays eight customer journeys against it.
  5. Roll back. If the release is not healthy or a journey fails, the previous release is started again and the job fails.

9 Decision records

Seven records in the brief's five fields, with the chosen option in bold. Record 2 is a formal file in the repository, docs/adr/0001-degraded-mode-when-the-network-api-fails.md, accepted on 16 November 2026. The other six are recorded in the execution plan as design rules, assumptions and decisions, and are written up in record form here. Their files are still to be written.

Reference first: the API answers before anything is checked

RECORD 1 · DESIGN RULE 1

Decision
Every contact must get a reference within 2 minutes, even in a tenfold surge with a system down. When does the API reply?
Options
A. Check the customer, the network and the model, then reply with reference and answer together. B. Queue every contact for a worker to create the case. C. File the case and reply at once.
Choice
C. The case, its reference and the follow-up work are one transaction. The API replies before anything else is called.
Why
The reference then depends on the database alone. No model, SkyLink system or backlog can delay it. Slowest reference in the surge test: 0.253 s, against a limit of 120 s.
Trade-off
The answer to the question arrives separately, and the page has to fetch it. For a short time the reference exists only in the platform's records. Regulatory Affairs has yet to confirm it as the official complaint number (D5, open).

An unreadable network status is unknown, never clear

RECORD 2 · ADR 0001 · THE CURVEBALL

Decision
Network Monitoring fails in the middle of a live outage. What is a customer told whose node cannot be checked?
Options
A. The last known status with its age. B. Treat no answer as no outage and give the router steps. C. A third answer: unknown.
Choice
C. Outage, confirmed clear or unknown. The feed can still prove an outage. Only a fresh live reading proves there is none.
Why
"No outage reported, as of 20 minutes ago" is read as "no outage", and the first minutes of an outage are when an old answer is most wrong. In 8 of 8 failure drills there is no false all-clear and no visit on old information.
Trade-off
While the API is down, a customer on a healthy node gets no help with their own equipment and is with a person after about five minutes. A long failure fills the staff queue: 2,693 of 3,361 such contacts in the half-hour run (D11, open).

One writer: specialists propose, the executor acts

RECORD 3 · DESIGN RULE 5

Decision
Some outcomes need a change in SkyLink's systems: a ticket, a credit, a booking, a text. Who may make it?
Options
A. Each specialist acts for itself. B. A separate service for each specialist. C. Specialists propose, and one program acts.
Choice
C. Specialists hold read-only keys and write proposals. The executor holds the only write key and checks each one again.
Why
One place to check again, one key to guard, one place where "exactly once" is enforced. Whatever a specialist is tricked into believing, it holds no key that writes. A write whose answer was lost is replayed into one ticket.
Trade-off
Actions happen a moment after the turn, so the customer hears the outcome in a second message. The separation is between programs. Inside the orchestrator the specialists share its four read-only keys.

The database is the queue

RECORD 4 · EXECUTION PLAN, SECTION 4

Decision
The parts leave work for each other: new cases, wake-ups, proposals. Where do those notes live?
Options
A. A message broker, Kafka or a cloud queue, beside the database. B. Rows in the database we already have, claimed under a lock. C. Direct calls between the programs.
Choice
B. Notes for the orchestrator and proposals for the executor are rows in the same PostgreSQL database as the cases.
Why
A note and the thing it is about are saved in one write, so neither exists without the other, and there is one system to run and back up. 13,941 of 13,941 contacts were accepted in a half-hour run at up to ten a second, on one laptop.
Trade-off
The database is a single point of failure and a ceiling on volume. For a larger deployment the design maps onto Amazon SQS FIFO with one ordered lane per conversation. That step is on paper.

The language model fills in a form

RECORD 5 · DESIGN RULE 2

Decision
A language model is good at understanding what people write. How much of the job should it do?
Options
A. An agent with tools: the model decides and calls SkyLink's systems itself. B. Rules decide and the model words the replies. C. The model describes the message in nine fields, rules decide, and pre-written messages speak.
Choice
C. The model describes and code decides. It has no tools and writes nothing a customer reads.
Why
The model's worst possible mistake becomes a wrong tick on a form. It cannot name an amount, declare the network healthy or put a sentence before a customer. 61 of 61 attack runs pass, 18 with a scripted model that obeys the attacker.
Trade-off
Conversations are less flexible. 35 fixed messages cannot answer everything, and unusual requests go to a person. The fallback keyword rules are cruder than the model.

AWS, in the Mumbai region

RECORD 6 · CLIENT DECISION D4, EXECUTION PLAN

Decision
The brief asks for a cloud choice on AWS or Azure, and for the argument behind it.
Options
A. Amazon Web Services, Mumbai. B. Microsoft Azure, an Indian region, with equivalent services. C. No cloud: demonstrate from a laptop only.
Choice
A, decided on 22 November 2026. The demonstration runs there, for about $1.90 a day.
Why
The team had access to AWS, the action plan's reference target: the shortest safe route to a running demonstration. Nothing in the design is tied to one cloud: containers and PostgreSQL run the same on Azure. Mumbai is close to the team and the audience.
Trade-off
One server and one database, each in a single zone, with no load balancer. If either fails the demonstration stops, and each release interrupts it for about 25 seconds. No claim is made that AWS is cheaper or better in general.

No churn model: one open rule in its place

RECORD 7 · ASSUMPTION A10, EXECUTION PLAN

Decision
The brief names repeat complaints as the top churn signal and maps a churn score to the ML tools of layer 6. Build one?
Options
A. Train a churn model and treat high-risk customers first or better. B. One open rule: two or more contacts in seven days raise a case's place in the staff queue. C. Ignore churn.
Choice
B. No model. The rule never changes what a customer is owed.
Why
The data holds no record of who left, so a model has nothing to learn from. Treatment by predicted churn risks the unfair offers by segment that the brief rules out. Consumer and small-business customers end the same way in 8 of 8 matched situations.
Trade-off
No early warning of churn, and no measured churn benefit. Both need real outcome data and a fairness review first.

10 Limits: what is not built, and what a pilot would change

Not built Not built

  • Metrics, dashboards, alerts and a runbook (milestone M5). What exists: an audit trail for each contact, redacted logs, optional traces with contents hidden, and the staff desk's operations queue.
  • Machine learning: no churn score, no anomaly model, no learned embedding model.
  • More than one server, a load balancer, a standby database, and blue-green or canary releases.
  • A private link to real SkyLink systems. The on-premises side is simulated.
  • Real staff sign-in, a database role for each program, and a second identity factor for visitors.
  • A retention job, and export or erasure of a customer's data on request.
  • From the staff desk: a reply to the customer, and a takeover button (the API route exists).
  • A cost estimate for a pilot, and six of the seven decision records as files.

What a production pilot would change On paper

  • One server becomes two copies of each program (one feed consumer) across two zones, behind a load balancer.
  • The simulator becomes SkyLink's real systems, behind a gateway SkyLink runs, over a private link. A dedicated line or a tunnel is for SkyLink's network team to choose.
  • The notes between the parts move to a managed queue and the events to a managed stream. The database gets a standby.
  • Fixed keys become short-lived ones, issued by SkyLink's identity system.
  • The real data pack, guides, credit policy and API contracts replace the stand-ins, at adapters/ and pipelines/.
  • Regulatory Affairs rules on where the language model may process messages. The keyword rules, which send nothing anywhere, stay the default.
