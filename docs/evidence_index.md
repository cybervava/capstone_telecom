# Evidence index for the supporting checklists

The brief: "Every ticked item needs evidence in the submission (screenshot, test case, config
line or log). An unticked item needs a one-line reason." This is checklists 1 to 3, line by
line. Checklist 4 (operations readiness) belongs to M5.

☑ ticked, with the evidence. ◐ ticked in part: what is shown, and what is not. ☐ not ticked,
with the reason. Everything is measured on synthetic stand-in data (assumption A1).

To see the evidence run: `make up`, then `make test-all` (tests), `make eval` (reports in
`evals/reports/`), `uv run python scripts/attack_suite_can_fail.py` (that the attack suite
can fail).

## 1. Guardrails

| | Line of the checklist | Evidence |
|---|---|---|
| ☑ | Input guardrail: prompt-injection and jailbreak checks on all free-text user input and on retrieved documents | **Input.** Every message is looked at by keyword rules beside whoever reads it; known injection phrasing in a message that reports no fault is declined whatever the reading (with a fault reported in plain words the message goes its usual way, and can unlock nothing), and a flagged message leaves an audit entry (`llm/offline.py` `second_look`, `orchestrator/routing.py`, `guardrail.input`). `tests/e2e/test_flagged_messages.py`; attack suite A1 to A7. **Documents.** No model reads a guide; steps are quoted. A step that speaks to an assistant, of money, asks for a code or sends the customer to a number or an outside address is refused when the index is built and again when it is about to be sent (`rag/documents.py` `not_a_step`). `tests/unit/rag/test_documents_and_embedding.py`; attack suite B1 to B4, B7, B8. The stronger evidence is that injection has nothing to reach: the model has no tool, and the 18 attacks that lie in how a message is read are also played with a model that obeys the attacker |
| ☑ | Input guardrail: PII detection and masking before any call to an external model | `guardrails/pii.py`; `tests/unit/llm/test_model_payloads.py` (the details of 300 customers written into 15 messages, searched for in the request the Claude provider would send); attack suite G1. An unidentified visitor's text is not sent to a model at all: G2. What masking cannot know is said in `docs/threat_model.md` (LLM02) |
| ☑ | Output guardrail: answers grounded in retrieved sources; ungrounded answers blocked or flagged | Customers are sent templates built from evidence; troubleshooting steps are quoted from the guide of the customer's own router and checked again when sent (`agents/troubleshooting.py`). A message that claims more about the network than the evidence of that turn backs is stopped where it is stored, recorded as `message.blocked`, and a person takes over (`guardrails/claims.py`, `orchestrator/outgoing.py`). `tests/e2e/test_message_claims.py`; attack suite A4, B4, B5, F1; `evals/reports/curveball.md` |
| ☑ | Output guardrail: citations shown for every policy, SOP or regulation claim | Quoted steps end with `Source: <guide> §<section> v<version>` (`agents/replies.py` `guided_steps`; `tests/e2e/test_guided_troubleshooting.py`). A credit message names the policy version it was worked out from (`tests/e2e/test_service_credits.py`). What is said of an outage carries the time and the source of the evidence. The assistant states no regulation to customers |
| ☑ | Output guardrail: toxicity and off-topic filters; agent refuses out-of-scope requests politely | Nothing the assistant sends is generated text, so there is nothing of its own to filter. Abuse and off-topic requests are declined with one polite message that still carries the complaint reference; a fault reported rudely is handled as a fault. `tests/e2e/test_flagged_messages.py`; attack suite H1 to H3 |
| ☑ | Action guardrail: every tool has an allow-list, typed inputs and limits (amount, count, scope) enforced in code, not in the prompt | A key for each agent identity with the scopes of its tools (`mock_oss/auth.py`; `tests/mock_oss/test_auth.py`, `tests/contract/`; attack suite I2). Every call has a typed request and response (`adapters/models.py`). Limits in code: the amount is the policy's, between its minimum and the monthly fee (`domain/credit.py`; `evals/reports/credit_policy.md`); one credit per service per outage; one open visit per service (migration `0007`). The prompt holds no rule |
| ☑ | Action guardrail: high-impact actions (credit above limit …) require human approval | A credit above INR 500 waits for a supervisor. At or under that it is applied without review as the stack runs (`CARE_CREDIT_REVIEW_ALL=false`, decision D3 of 23 Nov); the tests and the attack suite run with every credit waiting for a person. The approval is bound to the hash of the request that was shown, the role is checked at the API and in the repository, and a rejection must give its reason. `tests/integration/api/test_approvals_api.py`; attack suite C1 to C5 |
| ☑ | Loop guardrail: maximum steps, maximum tool calls and timeout per request | Decisions in one run of the workflow: 12, then a person (`orchestrator/routing.py` `MAX_STEPS_PER_RUN`; LangGraph's own ceiling of 60 steps stands behind it, `graph.py`). Each step: 30 s and two attempts (`graph.py`). Asks for identity: 3. Re-checks of an unverified network: 5, or 15 when a node fault is suspected (`CARE_NETWORK_RECHECK_LIMIT`, `CARE_SUSPECTED_WAIT_SECONDS`). Tries of a failed turn: 5, then a person. A model call: 8 s, then the keyword rules. Gateway calls: a timeout each, a circuit that rests a failing dependency. Tool calls are not counted as such: each step makes a fixed, small number, so the step limit bounds them. `tests/unit/orchestrator/test_routing.py`, `test_routing_events.py`, `tests/unit/llm/test_gateway.py`, `tests/e2e/test_reliability.py`, `test_resting_dependencies.py` |
| ☑ | Confidence threshold: low-confidence cases routed to a human with a summary | An identified customer's fault or billing reading below 0.5, a reading the rules cannot place after a model failed, and a reading of "nothing of ours" that contradicts the customer's plain fault report all go to a person (a reading of "other" is otherwise declined politely, and "it works" after the assistant asked closes the case, at any confidence) with a summary built from the recorded facts (`orchestrator/routing.py`, `handover.py`). `tests/unit/orchestrator/test_routing.py`; attack suite J3 |
| ☑ | Guardrail test set of at least 15 attack and edge prompts, with pass rate reported | `evals/reports/attack_suite.md`: 40 attacks, 58 runs, 58 passed (100%), no critical failure. As first measured 50 of 56 passed; the five gaps it found were closed (M4 slice D). That the suite can fail: `scripts/attack_suite_can_fail.py`, 27 checks: 25 removed controls each reported by the attack meant for them, and 2 where the second of two locks is shown still to hold |

## 2. Security

| | Line of the checklist | Evidence, or the reason |
|---|---|---|
| ◐ | Secrets in a vault or managed secret store; none in code or logs | **In the demo on AWS, a managed store**: the host's settings are the secret `skylink-care-demo/env` in Secrets Manager, written once with fresh secrets by `deploy/aws/operate.sh env-init` (so the host shares none with a laptop), read at every start by the host's role, and never part of Terraform's state (`deploy/aws/terraform/iam.tf`). | ◐ | Least-privilege IAM: each agent has its own identity and only the permissions its tools need | At the gateway: yes. Users reach the site over HTTPS, with a Let's Encrypt certificate, and nothing but 80 and 443 is open (`deploy/aws/Caddyfile`, `deploy/aws/terraform/host.tf`). Inside the host the containers talk plain HTTP on Docker's network; a laptop stack has no TLS |

## What this index does not claim

- That the numbers are SkyLink's. The policy, the complaint rules and the data are stand-ins.
- That a live language model withstands attack in general. The suite was run once with
  OpenAI's `gpt-5.4-mini` reading the 18 attacks made of words (58 of 58 runs passed, the
  model made all 24 readings: `evals/reports/attack_suite_openai.md`); one run says little
  about how often a model is moved. Claude was not run (no key). The demo uses that model
  (decision D2), pinned to the snapshot of the run. The other evaluations ran on the keyword
  rules.
- That the demo on AWS is a production deployment. It is one host, with one shared sign-in at
  its edge, run with `CARE_ENV=dev` for the staff sign-in; a retention job, a database role
  for each process and a real sign-in for staff are named above as missing.
