Flow 2 of 9 · 19 steps

Fault at home: the guide lookup

The node is healthy and the customer's own line passes its test, so the problem is most likely in the home. This is where retrieval (RAG) is used: a search finds the sections of the guide, a language model (where one is configured) chooses among them, and code checks what it chose before anything is said.

The customer writes

“my wifi keeps dropping”

How it endsThe customer gets steps quoted word for word from the guide for their own router, with the source and, where a model pointed at them, their own description and the guide's sentence as quotations. If the steps do not help, a person takes over.

  2. Intake, pick-up, triage and the first routing: the same for every new contact.

  • care-apiFront desk: takes the message, returns the reference
  • care-workerCoordinator and agents: reads, decides, proposes
  • care-adminRun once, before any request

Network Monitoring is down

The curveball: the Network Monitoring API stops answering in the middle of a live outage. The platform must not say "all clear" when it cannot check.

The customer writes

How it endsThe reference is still issued at once. The customer is told the status cannot be verified, or of the outage if the feed still proves it. After five minutes without a verified answer, a person takes over.

The NOC declares an outage. Customers on the affected node are told before they ask, if they have agreed to such messages.

Flow 8 of 9 · 8 steps

Close-up: how a message is read

The language model's first job, step by step: one message in, nine fields out (its second, choosing a guide section, is in flow 2). It decides nothing about the network, credits or visits, and writes nothing a customer reads.

The message being read

“Hi, this is Asha Menon from Indiranagar ... My wifi has been down since morning.”

How it endsA TriageReading and the rules' second look, recorded with the model and prompt version. Routing then acts on it only within what the evidence allows.

Flow 9 of 9 · 6 steps

Another assistant asks: the MCP server

A supervisor's desktop assistant, or any other Model Context Protocol client, may ask the platform three things and how the platform itself is doing. It reads and cannot act. The assistant in the customer's path does not come this way and is given no tool.

An MCP client calls

check_network_status("BLR-OLT-0012")

How it endsAn answer by the platform's own rule, with the sentence that says what it may be used for, and an entry in the audit log. Nothing in SkyLink's systems changes.

  • care-mcpMCP server: read-only tools for other assistants

Where the code comes from. Every excerpt is cut from this repository as it stood at commit 772467c (25 Nov 2026): 155 excerpts from 59 files. The line numbers are the files' own, and a marked gap means lines were left out to keep an excerpt short. When the code changes, this page does not: check the file before quoting a line.

What "AI" means here. There is no trained machine-learning model in this codebase. A language model reads one message into nine fields and, for router advice, chooses among the guide sections found; it is switched off by default. Retrieval filters and ranks 96 sections of router guides and quotes them word for word. One probability formula spots a node fault before the NOC declares it. Everything else is rules in plain code.

Make-believe, on purpose. SkyLink Telecom is a fictional company from a training brief. Its customers, network, credit policy and systems are invented stand-ins. The plain-language guide to the same code is docs/HOW_IT_WORKS.md.
