Stop 1 of 8 · The idea

Two kinds of traffic, one careful office

SkyLink Telecom is the fictional operator in our capstone case study. Its care team has to handle two very different kinds of traffic at once: customers who ask and wait, and a network that announces faults nobody asked about. This page shows in plain words how the system we built joins the two, where it runs, and why each part is built the way it is.

The office, in six parts

Think of the platform as a small, very disciplined customer-care office, in which each part has one job.

  • Front deskTakes every message, hands back a complaint reference at once, and does nothing else.
  • Case filesOne database that holds everything, including the notes the parts leave for each other.
  • Coordinator and specialistsWork each case through its steps. They may look at SkyLink's systems. They may not change them. The case study calls them the orchestrator and the specialist agents.
  • The handsThe only part allowed to change anything in SkyLink's systems, after checking again. The case study calls it the Action agent.
  • The radioListens to the network team's announcements and wakes any conversation waiting for that news.
  • Staff deskWhere people approve credits and pick up what the assistant hands over.
See them work together

The one rule everything rests on

The parts that read and decide are not the parts that act.

Nothing the assistant reads, and nothing an AI model says, can move money or send a technician by itself. Each such action is first written down as a proposal. Different code, holding a different key, checks it again at the moment it is carried out.

  • A complaint reference comes first, before anything else is asked or checked.
  • Evidence decides. Language only explains.
  • "I could not check" is never treated as "all clear".
  • Only one part can change anything in SkyLink's systems.

Built Design rules 1, 2, 3 and 5 of the build plan. Each is held in place by automated tests.

What is real here

The software is real and it runs: six programs, 2,662 automated tests, seven scored evaluations, and a demonstration deployed on Amazon Web Services on 22 November 2026. The world around it is make-believe. SkyLink's customers, network, credit policy and back-office systems are invented stand-ins, because the real ones were never supplied. The design for a real pilot goes further than what is built, and this page marks the difference each time.

          Stop 5 of 8 · Cloud

          Part in the cloud, part in SkyLink's own building

          A telecom company's core systems, such as network monitoring, customer records and billing, usually stay in its own data centres. Engineers call that . The care platform is new and can run in a rented . A design that spans both is called , and the line between the two halves is the most important line on the map.

          What a pilot would change

          • One server becomes several copies in two zonesToday one rented server runs every program. A pilot would run at least two copies of each across two of the Mumbai region, behind a load balancer, so that one failure does not stop the service.
          • The stand-in becomes SkyLink's real systemsToday a simulator on the same server plays SkyLink's six systems. A pilot connects to the real ones in SkyLink's data centre, through a that SkyLink runs.
          • A private link appearsNothing crosses to a real data centre today. A pilot needs a private, encrypted connection: a dedicated line or an encrypted tunnel over the internet. Which one is for SkyLink's network team to decide.
          • The database stops doing two jobsToday the notes between the parts live in the database. The design maps them onto a managed with one ordered lane per conversation, and maps the network announcements onto a managed .
          • The database gets a standbyToday there is one managed database in one zone, backed up daily. A pilot adds a standby copy in a second zone.
          • Fixed keys become short-lived onesToday each specialist has a fixed key. In a pilot, SkyLink's own identity system would issue short-lived credentials to each one.

          Target design On paper only. No private link, queue, stream or second server has been built or tested. The team's action plan names the same services and warns against claiming a working link to a data centre when only stand-ins have been tested.

          Rules at the boundary

          Whatever the link is made of, these rules already govern every call across it.

          • Three programs may crossThe coordinator to read, the radio to listen, the hands to act. The front desk never calls SkyLink's side.
          • Every call has a deadlineOne second to connect and nine seconds in all. A line test may take ten.
          • A failing system is restedAfter five failures in a row it is not called for 10 seconds, then tried once.
          • A failed call is a failureIt is never turned into "nothing found", and never into "all clear".
          • A read may be tried once more. A write may not.Only the hands repeat a write, and only under the same unique label.
          • The customer's profile stays where it isIt is read when needed and not copied into the platform's database.

          Built Each rule has tests. The drills that play these failures are described under Parts.

          AWS or Azure?

          The team chose Amazon Web Services on 22 November 2026, for three reasons. The team had access to it and experience with it. Nothing in the design is tied to one cloud, because containers and PostgreSQL run the same way on either. And its Mumbai region keeps the demonstration close to the team and the audience. We do not claim that AWS is cheaper or better in general.

          How a release gets there

          1. Every check runs firstCode style and types, 2,662 automated tests, the seven evaluations, and a scan for leaked secrets.
          2. One image is built and scannedThe programs are packed into one image, which is scanned for known weaknesses.
          3. It is stored under its own nameEach image is named after the exact version of the code, and a name can never be moved. A rollback gets what was tested.
          4. The server starts it and tests itselfThe server plays eight customer journeys against itself. If one fails, it starts the previous release again.

          Measured The first release that passed, on 22 November 2026, took 15 minutes from push to live. The site was down for 24 seconds and the eight journeys took 55 seconds. A rollback was tried once, back and forward again, in about two minutes each way.
